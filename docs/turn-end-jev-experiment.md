# Turn-end-triggered Jev experiment (#10)

## Signal investigation

The [GPT-Live conversation guide](https://developers.openai.com/api/docs/guides/live-conversations) says `session.input_transcript.delta` has no item ID or completed-turn event, and delivery can be uneven. The [Live API reference](https://developers.openai.com/api/reference/cli/resources/live) likewise says these deltas do not define complete turns or include a transcript-done event. The [migration guide](https://developers.openai.com/api/docs/guides/live-migration) makes clear that Realtime's completed-transcript and response-done events do not have corresponding GPT-Live events. Sprout's WebRTC data channel receives transcript fragments, context acknowledgments, usage, delegation and session lifecycle events; none marks input speech stopping. GPT-Live controls its own speech turn and cannot be used as a count-completion signal when the prompt asks it to remain silent pending Jev.

The selected fallback is **local microphone activity** from the already-granted audio track. A small browser energy detector emits `microphone.speech_started` and `microphone.speech_stopped`; it keeps no audio samples, uses an adaptive idle noise floor, and requires 900 ms of quiet before stop to bridge ordinary between-word pauses. Jev starts after a further 250 ms transcript-tail window to let GPT-Live deliver a final fragment. A new fragment restarts that tail window. The existing 1,500 ms transcript-inactivity path remains only for missed activity detection or unavailable Web Audio, and the debug panel names which path fired. These numbers are turn-detection policy, not provider guarantees. In particular, a pause longer than 900 ms can still be misread as a completed turn; this must be checked in the live experiment.

## Behavior and safety

Only utterances containing an explicit digit or number word reach Jev; simple `Yeah` and `I don't know` responses do not consume a request. The existing pinned `jev-1.13.0` Noul question and 0.90 threshold are unchanged. A microphone speech start cancels a pending turn-end trigger, aborts an in-flight Jev request, and invalidates its result even before a new transcript arrives. The app still owns scene state; a confident current result commits the next scene, React displays it, and only then does the app append new-scene context to GPT-Live. A substantive Sprout reply defers that commit until the existing output transcript quiet boundary. An unavailable result stays neutral.

`?debug=1` now shows the trigger, transcript receipt time, detected turn-end and request times, request latency, detected-end-to-decision and detected-end-to-display times, stale/cancelled results, and speech deferral. For microphone VAD it also shows the measured quiet interval, an estimated acoustic speech-end timestamp at the first quiet audio frame, and estimated-acoustic-end-to-decision/display intervals. Transcript times are receipt times; provider `start_ms`/`end_ms` remain approximate speech intervals in the exported event log. None proves precise final-word timing or audio playback.

## Comparison and outcome

PR #9 baseline: fixed transcript settle of about **1,500 ms**, successful transcript-to-decision **1,723–1,881 ms**, and Jev **222–405 ms** in its latest instrumented live run. This experiment measures the replacement path in a fresh live run below. The synthetic microphone uses adult text-to-speech on a fixed timeline, so it cannot demonstrate a preschool learner's natural timing or a listener's subjective sense of dead air.

### Fresh synthetic-microphone run

The `turn_end_experiment` run on 2026-09-23 used real `gpt-live-1` and Jev via the local route, with macOS text-to-speech fed into Chromium as the microphone. The ignored artifact `test-results/live-matrix/turn_end_experiment/` contains the timestamped local log. It is a live service test but **not** a human listening session. No subjective smoothness claim is justified.

Four advances were observed and no false scene advance was observed. The three immediate advances displayed 525–923 ms after the last received learner transcript fragment. That display interval and PR #9's transcript-to-decision interval have different endpoints; a decision-to-decision comparison using the same transcript-receipt anchor appears below. The fourth required speech deferral. GPT-Live's premature praise is a failure of the conversational gate despite the existing prompt; the app did preserve scene/display ordering and did not transition during its substantive speech. The scripted “Wait, I am still counting” arrived after the deferred scene had displayed; it did not test an in-flight correction to the earlier approved answer.

### `?debug=1` timing and stale-result rerun

The `turn_end_debug` run used the same real services with `?debug=1`; its exported in-memory diagnostic file is `test-results/live-matrix/turn_end_debug/diagnostics.json`. The detector reported `microphone_vad` on each spoken line. For five current Jev decisions, VAD detection → request was **250–267 ms** and VAD detection → decision was **538–831 ms** (median 700 ms). Jev itself took **288–579 ms** (median 433 ms). Four advances displayed **567–867 ms** after VAD detection (median 783 ms); each new-scene instruction followed the DOM display by 21–31 ms in the browser log. These intervals omit the preceding 900 ms minimum microphone quiet period. The fixed 1,500 ms transcript path was not used for these decisions.

The deliberate two-part answer on two ducks revealed an important boundary: the microphone detector marked “One” as a turn end and sent it to Jev after the 250 ms tail. The next speech began while that request was in flight; the app aborted it and recorded `STALE` at 30.153 seconds on the page clock. It then evaluated the completed “One Two ducks” once and advanced. There was no false advance in this case because the incomplete “One” could not correctly answer the two-duck scene, but the run demonstrates that the local detector does not know whether a learner is done thinking. A sufficiently long pause after an initially correct count could still cause premature approval. A local energy detector is not an authoritative conversational endpoint.

This run made no Jev request for “Yeah” or “I don't know,” stayed on “Five” for three strawberries (0.02), and evaluated the self-correction “Two. No. Three” as 0.97. It refused six unsolicited GPT-Live delegations without changing the scene. Its received output transcript before approval was silence or a one-word neutral acknowledgment for each current evaluation; as in the first run, browser transcript timing cannot prove what was audible at the exact decision instant.

The first run's premature praise is serious enough that the final implementation adds one narrow prompt sentence forbidding “yes,” “that's it,” “right,” or naming the total before the app update. The final prompt version is `counting-jev-3`; the Jev question, model, threshold and scene sequence remain unchanged. A final live run checks this prompt change below.

### Final production-build run and decision

The final `turn_end_debug` scenario ran against a production build with `?debug=1` and `counting-jev-3`. Its exported diagnostics and browser timeline are in the ignored `test-results/live-matrix/final/turn_end_debug/` directory. All current evaluations used `microphone_vad`. VAD detection → Jev start was **250–350 ms**; Jev took **342–552 ms**; VAD detection → decision was **592–902 ms**. Three immediate advances displayed **616, 735 and 933 ms** after VAD detection, and the app's new-scene instruction followed each display by 23–30 ms. The fourth correct answer was approved in 766 ms but held while Sprout was speaking; the scene displayed **3,667 ms** after VAD detection, including a 2,874 ms deferral. No scene changed during that substantive output transcript. These values omit at least the configured 900 ms quiet period: estimated acoustic speech end → decision is approximately **1,492–1,802 ms**, before uncertainty about the first quiet audio frame and transcript delivery. This estimate is derived from the configured threshold; the historical run did not record the actual quiet interval.

The deliberate two-part “One” / “two ducks” again started one request for the partial “One.” New microphone activity aborted it, and the cancelled result was logged `STALE` before any scene change. The completed answer scored 0.95 and advanced. “Yeah” and “I don't know” used no Jev call. “Two. No. Three.” scored 0.97 and advanced on the final correction. “Five” on three strawberries scored 0.02 and stayed. The final three-count scored 0.98 and advanced after the deferred speech boundary. The browser log recorded no explicit correctness statement before approval on the immediate advances in this run; on the deferred count it recorded a substantive but neutral “Ooh, that sounded careful.” The earlier run's premature “Yes, that's it!” remains a real failure case for the pre-approval speech requirement. Output transcript arrival and playback are not the same clock, so this cannot prove precisely what the child heard before approval.

Using the same **last learner transcript receipt → Jev decision** anchor, PR #9's latest instrumented successful decisions were **1,723–1,881 ms** and this PR's final run had **697–804 ms** across five current decisions (`transcript_to_decision_ms` in the saved diagnostics). That shows an improvement in transcript-receipt-to-decision latency for these samples. It does not establish faster final-word-to-decision or final-word-to-display latency, because transcript delivery is uneven and neither run measured acoustic speech end. The new turn-end path also does **not** establish a reliable end of the child's intended answer: the long pause caused an early partial Jev request in both debug runs, and a fast result on an initially correct partial count could still commit before a later correction. The prompt cannot guarantee that GPT-Live will withhold correctness speech, and one deferred advance was much slower. Noise, low speech energy, and preschool speech have not been validated. A human listening session was unavailable; the fixed-timeline synthetic run cannot rate subjective dead air or conversational smoothness, though the 2.9–8.7 s deferrals are likely noticeable (inference).

**Decision: option 2 — this interaction is not yet good enough for the MVP's turn-taking guarantee.** The remaining latency and turn-taking problems justify a separate speculative-Jev experiment, but speculation alone cannot solve premature endpoint detection or pre-approval GPT-Live speech. Those controls need their own evidence before using speculative results. No speculative Jev work is implemented here. This PR is an experimental implementation with a documented negative conclusion, suitable for review rather than deployment on the strength of these synthetic runs alone.

## Follow-up: bounded correction window

A regression test showed that Jev could confidently approve “One” on the one-duck scene and the app could commit the next scene before a later “no, two” correction began. The test that paused after “There are” did not exercise this case because that phrase contains no number. The app now holds every approved scene advance until 2,500 ms after the later of detected turn end and the last learner transcript receipt. Renewed microphone activity or a newer learner transcript cancels the approval; a substantive Sprout reply can extend the hold until its output transcript is quiet. Jev still starts after the 250 ms VAD transcript tail, so a result can be ready during the correction window.

This is a bounded policy, not proof that a learner has finished. A correction after the window can still arrive too late, and normal advances now wait longer than the earlier live-run timings above. The earlier measurements predate this change. A fresh live listening run is needed before claiming the turn-taking guarantee or comparing end-to-display latency again.

## Follow-up: provisional microphone activity

The energy detector previously treated one loud audio frame as speech start. That immediately cancelled a pending Jev result or approved advance; a click or echo without a child transcript could leave a valid count unadvanced. The detector now reports provisional activity on the first loud frame and confirms speech only after 80 ms of voiced activity. A burst that goes quiet for 150 ms before confirmation is discarded. The session pauses pending work during provisional activity, then resumes an unconfirmed burst's prior decision after a 1,500 ms transcript grace period. A child transcript arriving during the burst supersedes the prior decision and is evaluated after confirmed VAD stop or the transcript fallback.

Confirmed microphone activity still invalidates the prior decision immediately. If it stops without a new transcript, the app leaves the scene in place and asks the child to repeat after the fallback window. No transcript is not proof that a correction was absent, so this path does not automatically reapprove the old answer. Loud toy noise lasting long enough to pass onset confirmation can still cause a repeat request; low-energy or very short real speech can still be missed. These thresholds and recovery behavior have unit coverage but no fresh live listening evidence.
